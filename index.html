01 · Identidad

Identificar al usuario

Usuario actual: anónimo · Device ID: —

Particularidades
  • changeUser no tiene vuelta atrás: un navegador identificado no vuelve a ser anónimo. Para "desloguear" se usa wipeData(), que borra todo lo local y genera un device nuevo.
  • Lo que hizo el usuario mientras era anónimo se fusiona con el perfil identificado si ese external ID todavía no existía.
  • Para encontrarlo en el dashboard: Audience → Search Users, por external ID o email.
  • Esta demo no usa SDK Authentication (Settings → App Settings), porque necesita un backend que firme un JWT por usuario y esto es un sitio estático. En un cliente real conviene activarla: el backend firma en el login, la web llama a changeUser(id, jwt), y se prueba primero en "Optional" antes de pasar a "Required".

02 · Eventos

Custom events

Particularidades
  • El SDK manda los datos en tandas cada pocos segundos. Esta demo llama a requestImmediateDataFlush() después de cada acción para que aparezcan antes.
  • Un evento nuevo aparece en Data Settings → Custom Events recién cuando llega el primero. Hasta entonces no se puede elegir como trigger de una campaña.
  • Las propiedades del evento se usan en Liquid como {{event_properties.${nombre}}} dentro de una campaña disparada por ese evento.

03 · Tienda

Carrito y compras

Placement : sin banner para este usuario.

Particularidades
  • logPurchase no es un custom event: va a Revenue y a Data Settings → Products, y se filtra con "Purchased product" en los segmentos.
  • "Agregar al carrito" sí es un custom event (agrego_al_carrito) con el producto y el precio como propiedades.

04 · In-app messages

Disparar un in-app

Particularidades
  • Crear una campaña In-App Message action-based con trigger "Perform custom event: demo_inapp".
  • El SDK baja los triggers al iniciar la sesión. Una campaña recién lanzada no aparece hasta la sesión siguiente: cerrar sesión con el botón de arriba y volver a identificarse.
  • Los mensajes HTML custom requieren allowUserSuppliedJavascript: true, que esta demo ya tiene.

05 · Banners

Banners por placement

Placements de esta página: (arriba) y (en la tienda).

Particularidades
  • Los placements se crean antes en Settings → Banner Placements, con el mismo ID que usa el código. Después se arma una campaña de Banner por placement.
  • Banners depende del paquete contratado: si el workspace no lo tiene, el SDK devuelve FEATURE_DISABLED (lo muestra el log).
  • Se refrescan al iniciar sesión y al llamar changeUser. A mano, requestBannersRefresh tiene un límite: 5 pedidos por sesión, y se recupera uno cada 3 minutos.
  • Si el usuario no califica para ningún banner, el placement vuelve vacío y se muestra el contenido de fallback.
  • Requieren allowUserSuppliedJavascript: true en el initialize.

06 · Content Cards

Feed de Content Cards

Particularidades
  • A diferencia del in-app, las cards quedan en el feed hasta que el usuario las descarta o vencen.
